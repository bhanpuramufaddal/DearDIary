# Stage Details

Per-stage spec: what each reads, what it produces, what tools it uses, and what's distinctive. Every stage runs as a `claude-agent-sdk` agent unless explicitly marked otherwise. See [01-design-decisions.md §Agent loop](01-design-decisions.md#agent-loop-is-the-default) for the toolset semantics; this doc focuses on per-stage substance.

## Stage 0 — Spec Seed

**Purpose.** Take a free-form prompt; produce the persona's identity record.

**Reads.** The user prompt only.

**Writes.**

- `personas/<slug>.yaml` — via the typed `write_persona_spec(slug, name, prompt_text, created_at_iso, seed_hex)` tool. Slug is derived from the prompt's identity signals. **No personality, no Big Five.** Used for filenames and re-runs.
- `internal/persona_origin.md` — via `Write`. A reasoning trace introducing the persona. Magazine-feature opening, 3–6 paragraphs of prose. Where they are in life right now. The biographical anchor everything downstream hangs from.

**Tools.** `Write` + `write_persona_spec`.

**Distinctive.** Idempotent — if `personas/<slug>.yaml` exists, the command warns and exits. No psychological prelude. The yaml is filename infrastructure; the origin doc is the first reasoning trace.

## Stage 1 — Persona Foundation (the inversion)

Four sub-stages. Generates psychological depth back-stage first, then *derives* `profile.md` from it. Order follows Goffman: back-stage truth exists prior to performance.

### 1a — Life Context → `internal/life_context.md`

A multi-section life narrative covering six domains: professional, family, health, relationships, finances, identity_and_purpose. Each section is prose. Cross-domain tensions are woven into the narrative naturally — not in a separate "intersections" block.

**Reads.** `internal/persona_origin.md`, `personas/<slug>.yaml`.

### 1b — Character Sketch → `internal/character_sketch.md`

The back-stage truth as a biographical sketch. Personality surfaces in prose where it matters (no Big Five prelude). Blind spots, failure modes, recurring patterns, identity roles, real relationship dynamics. The novelist's bible — 2,000 to 4,000 words.

**Reads.** Everything upstream.

### 1c — Judgment Reasoning → `internal/judgment.md`

An essay titled *"How [persona] decides what matters this month."* Walks through what fires them up, what they suppress, how context shifts these. Worked examples grounded in the persona's specific life. Behavioral biases named in prose where they apply. Sections cover the kinds of judgments a triage tool would face — but as essay, not schema.

**Reads.** Everything upstream.

### 1d — Profile.md (DERIVED) → `profile.md`

The lossy compression the digest agent reads. Reads character_sketch + judgment + life_context + Avery's sample profile (shape template). Written in the persona's own voice. Rule-shaped, aspirational, sometimes wrong. **The gap between this and the upstream truth is the structural drift — generated by the compression, never patched in.**

**Distinctive.** This is the only Stage-1 file the digest reads. Everything else stays in `internal/`. The deliberate inaccuracy of profile.md vs character_sketch.md is what gives the eval its teeth.

## Stage 2 — Cast

**Purpose.** Author the persona's relationships at the tier appropriate to each.

**Reads.** All of Stage 1.

**Writes.**

- `internal/cast.md` — P0–P1 cast members each get a multi-paragraph profile written as prose. Each profile covers who this person is in their own right, how they came to be in the persona's life, what they're working toward, what makes them go quiet, how they speak. P2 gets one paragraph. P3–P4 (recruiters, vendors, ambient noise) listed with name + role only. **No bulleted current_goals, no communication_quirks lists — sentences.**
- Rows in `persona.db.cast` (via `add_cast_member`): `(cast_id, display_name, signal_tier, role_brief)`. Only for code cross-reference. No interiority fields — the depth stays in the markdown.

**Tools.** `Read`, `Write`, `Edit` + `add_cast_member` (INSERTs into `cast`).

**Distinctive.** Tier dictates depth. P0–P1 get the novelist treatment; P3–P4 are stubs. The `cast` table is the thinnest possible cross-reference target — the depth lives in `cast.md`.

## Stage 3 — Day Archetypes

**Purpose.** Define what a "normal day" / "crisis day" / "recovery day" looks like for this persona.

**Writes.** `internal/day_archetypes.md` — prose descriptions of 5–7 archetypes (normal, crisis, deep_work, family_heavy, big_meeting, recovery, weekend). Each archetype described in narrative ("On a normal day, Avery…") with a rough schedule embedded inside the prose. Persona-specific.

**Distinctive.** No schedule templates as JSON. The archetypes are voice exercises — when Stage 7 needs to render a "recovery day," it reads the prose.

## Stage 4 — Channels

**Purpose.** Define the medium-to-conversation mapping for this persona.

**Writes.** `internal/channels.md` — inventory of channels and how the persona uses each. Written as prose. Which carries which kinds of conversation. Which tools matter.

**Distinctive.** Persona-specific. Avery's Slack vs Vikram's Bloomberg chat vs Henry's secure-email channel all behave differently. The prose explains usage, not capabilities.

## Stage 5 — Storylines + plans (the heaviest authoring stage)

**Purpose.** Author every storyline arc, every declared digest moment, every noise event, every planned artifact. **All plot lives here.**

**Reads.** All of Stages 0–4.

**Writes.**

- Per storyline, `internal/storylines/<storyline_id>/arc.md` — narrative arc prose only. Where this storyline sits at window-start, what's at stake, who's involved, how it will move. Cast members named as subjects of sentences explaining their dynamics, **never** in a `characters:` list. Where the storyline temporarily inverts stated suppression rules, the inversion is explained in narrative.
- Rows in `persona.db`:
  - `storylines` — one row per storyline (via `add_storyline`).
  - `declared_moments` + `moment_supporting_artifacts` — one row per declared digest moment that should surface on morning M ∈ Days 6–35 (via `declare_digest_moment(...)`): target_morning, section, priority, action_class, rationale (prose), and the artifacts that support it.
  - `noise_events` + `noise_effects` — one row per plot-level disruption (via `declare_noise_event(...)`): occurrence_date, triggers_artifact_id, plus child effect rows (each being SHIFTED / CANCELED / MODIFIED / DECLARED on some declared moment, with its own `effective_from`).
  - `planned_artifacts` — every artifact_id this storyline will produce (via `declare_planned_artifact(...)`), with target render date, kind, content sketch, is_decoy flag. Stage 7 renders the actual prose; Stage 5 declares they exist.

**Tools.** `Read`, `Write`, `Edit` + `add_storyline`, `declare_digest_moment`, `declare_noise_event`, `declare_planned_artifact` (each INSERTs into the matching DB table; see [10-storage.md](10-storage.md)).

**Distinctive.** Cross-storyline interactions (a noise event from storyline A affecting storyline B's moments) are allowed and reconciled at Stage 6. Density target: 5–10 storylines, each with 8–20 declared moments and 3–7 noise events. See [04-storyline-authoring.md](04-storyline-authoring.md) for the object hierarchy and lifecycle vocabulary.

## Stage 6 — Window Plan

**Purpose.** Sequence the 35 days; seed the calendar.

**Writes.**

- `internal/window_plan.md` — narrative outline of the 35 days. Walks through the window roughly week-by-week (5 weeks: warm-up week + 4 eval weeks). Storyline beats land where they naturally land. Which arcs are expected to resolve and roughly when. The warm-up/eval-window boundary at Day 6 is mentioned but not over-emphasized.
- Rows in `persona.db.initial_calendar_events` — recurring events + pre-scheduled meetings that exist at Day 1, 00:00 PT (including any board meetings, offsites, or anniversaries that fall within the 35-day window). The seed state for the calendar service emulator's on-demand replay.

**Tools.** `Read`, `Write` + `add_initial_calendar_event` (INSERTs into `initial_calendar_events`).

**Distinctive.** The plan is narrative; the calendar seed is structured. Both feed Stage 7.

## Stage 7 — Living the 35 Days (rendering only)

**Purpose.** Render pre-declared events in persona voice; write daily interiority; emit calendar ops.

35 sequential agent runs (Days 1–5 warm-up + Days 6–35 eval window). Plot is fully authored at Stage 5; Stage 7 only renders.

Each day's agent:

1. **Reads today's pre-declared events** by querying `persona.db`: `planned_artifacts WHERE target_render_date = N` and `noise_events WHERE occurrence_date = N`. These are the artifacts to render and the persona experiences to write today.
2. **Reads (prompt-cached) the foundation** — `character_sketch.md`, `judgment.md`, `life_context.md`, `cast.md`, `channels.md`, `day_archetypes.md`, `window_plan.md`, the storylines' `arc.md` files. Reads `daily_state/day_(N-1).md` for yesterday's state. Queries `calendar_ops` for prior calendar history if needed.
3. **Renders each pre-declared artifact** using `emit_email` / `write_note` / `add_calendar_op` — each INSERTs a row into the corresponding table. The artifact_id, kind, sender/recipient, target date are pre-declared; the agent supplies prose body (`body` column) in persona voice and the right tonal zone.
4. **Writes the day's experience** to `activity_log.md` and `internal/daily_state/day_NN.md` (markdown files) — journal entries covering what happened today, how it felt, energy state, what was noticed. Each open thread discussed by name. Interiority documents, not plot decisions.
5. **Texture-noise discretion only** — small ambient details (a slack ping, a 12-minute meeting overrun) that don't affect any declared digest moment.

**Tools.** `Read`, `Write`, `Edit`, `Glob` + `emit_email`, `write_note`, `add_calendar_op` (each INSERTs into the matching DB table).

**What Stage 7 does NOT do:**

- Invent artifacts beyond the pre-declared list.
- Author `planted_artifact_traces` (no longer needed — moments are pre-declared in the `declared_moments` table).
- Modify lifecycle effects on declared moments.
- Decide what tomorrow's digest should contain.

State propagation: each day reads prior day's narrative state. The narrative IS the cascade — Day N+1's voice references Day N's state by name. Continuity, not plot decision-making.

## Stage 8 — Artifact Emission

A single batched agent per persona that walks the day's `planted_artifact_traces` (or equivalent rendering queue) and INSERTs rows for any artifacts not yet emitted. Most artifacts are already INSERTed during Stage 7 as they're rendered; Stage 8 is a safety-net pass to catch anything that needs re-rendering (e.g., after a Stage 7 retry).

For each artifact pointer:

- Read the relevant trace, `daily_state`, `character_sketch`, `cast` (for the named other).
- Write the artifact in the persona's voice, in the appropriate **tonal zone**:
  - `public_front_stage` — press, outsiders, on-message.
  - `professional_front_stage` — investors, board, customers.
  - `internal_mid_stage` — team, trusted peers.
  - `private_back_stage` — self, spouse.
- Populate `x_synth_*` columns on the email/note row (Storyline, Tonal-Zone, Decoy, Source-Plan) so eval can read them without parsing prose.

**Tools.** `Read`, `Glob` + `emit_email`, `write_note` (each INSERTs a row).

**Stage 8B is gone.** The deterministic calendar replay used to materialize `calendar.ics` + 35 snapshot files on disk. With `calendar_ops` in the DB, the calendar service emulator computes any requested snapshot on demand by replaying ops up to a given date (`SELECT … FROM calendar_ops WHERE ts_iso ≤ :as_of ORDER BY ts_iso`). Same algorithm (`add_event` → new VEVENT, `move_event` → bump SEQUENCE, `cancel_event` → STATUS:CANCELLED, `decline_invite` → PARTSTAT=DECLINED), different home. No pipeline step.

## Stage 9 — Ideal Digest

Two phases. 9a (LLM, parallel-per-moment) does the substantive validation; 9b (deterministic walk) emits the morning files. See [08-validation-and-assembly.md](08-validation-and-assembly.md) for the full detail of both phases — what each validator checks, the assembly walk pseudocode, the morning JSON schema.

At a glance:

- **9a.** Spawn one validation agent per active declared moment. Each reads the persona's actual past as of morning M (via service emulator or direct DB queries scoped by date) and emits exactly one of `validation_pass` / `validation_fail` / `validation_correct` — each INSERTs a row into `validation_log`. With ~80–150 active moments per persona, this is the heaviest LLM workload after Stage 7.
- **9b.** A single SQL query joining `declared_moments` ⋈ lifecycle-resolved `noise_effects` ⋈ `validation_log`, partitioned by morning. The result writes 30 `ideal_digests/morning_NN.json` files. No LLM, no per-morning Python loop. See [10-storage.md](10-storage.md) for the query shape.

Optional: a thin LLM call per morning produces `morning_NN.reasoning.md` for human inspection. The structured JSON is deterministic regardless.

**Why Days 6–35 only.** Day 1 morning has no accumulated state — no carryovers, no stalled threads, no drift. By starting eval on Day 6, every morning faces ≥ 5 days of realistic accumulation, which is what production digests always face.
